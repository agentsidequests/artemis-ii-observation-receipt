# Artemis II standards and prior-art crosswalk

Date: October 10, 2026

Status: Bounded technical crosswalk for specialist review. It is not an OGC conformance claim, a PDS design decision, or evidence of NASA endorsement.

## Decision this crosswalk supports

The practical question is not whether PDS or geospatial ML already has metadata. Both do. The question is which existing concepts can carry the proposed Artemis II evaluation information, which task-specific relationships still need an explicit carrier, and which guarantees require executable evidence rather than descriptive metadata.

The recommended first implementation is therefore a linked prototype with three layers:

1. PDS LIDVIDs and archive versions remain the identity and source-of-truth anchors.
2. TrainingDML-AI concepts describe the task, samples, split roles, labels, provenance, quality, and changes where they fit.
3. A task-specific relationship table and validator declare protected parent groups and emit a content-hashed split receipt.

Only qualified PDS and OGC reviewers can decide whether a production version belongs in an existing product class, a Local Data Dictionary, an OGC encoding or extension, or a linked artifact outside either standard.

## Field-level crosswalk

The word “maps” below means that the existing construct can carry the same or a closely related idea. It does not mean that the proposed artifact is conformant, that exact cardinalities match, or that a particular PDS or OGC encoding has been approved.

| Proposed item | Existing construct that can be reused | What remains task-specific | Recommended prototype treatment |
| --- | --- | --- | --- |
| `product_lidvid` | PDS LIDVID; TrainingDML-AI sample `id` and `dataSources` can reference source identity | The PDS identifier must not be replaced by a locally invented sample key | Store exact LIDVID and use it as the immutable external reference |
| `source_snapshot` | PDS bundle or collection version; TrainingDML-AI dataset `version`, `updatedTime`, and changesets | Exact input-set identity and content hashes | Record PDS versions plus a deterministic manifest hash |
| sample membership | PDS collection inventory; TrainingDML-AI sample `datasetId` | A benchmark dataset may be narrower than the archive collection | Publish one row per included product and state the eligibility rule |
| split role | TrainingDML-AI sample `trainingType`; SomBench catalog `DATASET` | Excluded and unresolved states, plus the rule that produced the role | Use `training`, `validation`, and `test` consistently; add explicit `excluded` and `unknown` states in the companion contract |
| task | TrainingDML-AI `AI_Task` | Prediction unit, estimand, deployment population, unsupported generalizations | Add a versioned task profile that makes these decisions explicit |
| label source and provenance | TrainingDML-AI labels, labeling, labeler, and labeling procedure; PDS source references | Coverage, blank-state semantics, audit status, and task-specific label validity | Record source, method, coverage, unknown state, and review status |
| quality | TrainingDML-AI quality associations | The acceptance oracle for group reconstruction and split validity | Link descriptive quality to validator results without treating one as the other |
| `group_type` and `group_id` | TrainingDML-AI is extensible; PDS identifiers can anchor referenced products | No direct required action, temporal-run, or realized-episode group key was identified | Use a companion namespace that cannot be mistaken for a PDS LID |
| `group_authority` | PDS distinguishes archive products and references; provenance can describe derivation | Whether a key is archive-authoritative, mission-authoritative, reviewed-derived, or unreviewed-derived | Make authority a controlled field and prohibit silent promotion of derived keys |
| `membership_basis` | TrainingDML-AI `dataSources`, lineage, and labeling procedure; PDS source relationships | Exact reconstruction rule for non-label grouping | Store source references and a human-readable rule ID |
| `method_id` and `method_version` | TrainingDML-AI provenance and changesets | Executable implementation identity | Record tool version and, when feasible, source revision or artifact hash |
| `representation_role` | PDS product classes and source-product relations | Task-specific choice among source, raw, processed, and calibrated requirements | Reuse PDS semantics where available and state the task’s allowed roles |
| `position_in_group` and `observed_group_size` | No direct equivalent identified in the inspected conceptual model | Bracket position, action completeness, and sequence structure | Keep in the mission or task companion unless a specialist identifies an existing dictionary field |
| zero-to-many group-to-window membership | PDS references and TrainingDML-AI extensions can carry relations | Unmatched actions and overlapping planned windows cannot be forced into one owner | Use a separate relationship table with explicit unmatched rows and all memberships |
| `review_status` and `unknown_reason` | TrainingDML-AI quality and provenance can describe review context | A fail-closed distinction among unknown, unreviewed, machine-checked, and mission-reviewed | Use controlled values and require a reason when a required relation is unresolved |
| split algorithm and seed | TrainingDML-AI provenance or labeling procedure can describe process | Exact executable parameters and reproducibility | Put the exact algorithm version and seed in the receipt |
| input and output hashes | Revised TrainingDML-AI discusses hashes and signatures as integrity strategies | Hash algorithm, canonicalization, covered bytes, and verification result | Hash the canonical input manifest, assignments, and validator output |
| protected group keys | No direct required construct identified | The task-specific independence rule, possibly involving multiple group types | Declare one or more protected keys in the task profile and receipt |
| crossing violations and unresolved relations | Quality metadata may describe problems | Exact offending identities and a fail-closed decision | Emit every violation and unresolved case in machine-readable validator output |
| split receipt | SomBench materializes split assignments; Lunaris demonstrates a hashed manifest pattern | One signed or hashed account binding inputs, method, assignments, counts, violations, unknowns, and validator version | Generate a separate content-hashed receipt even if descriptive fields are also encoded in PDS or OGC metadata |

## What current practice changes in the recommendation

The prior version of the proposal risked making the PDS ML dictionary carry too much. The crosswalk changes the sequence:

1. **Confirm authority first.** The Artemis II data provider and coordinating PDS nodes identify which exposure, action, schedule, and episode keys are authoritative, derivable, or unavailable.
2. **Prototype outside a standards change.** Publish a small linked artifact for one frozen task, anchored to PDS LIDVIDs and mapped onto TrainingDML-AI concepts where the mapping is honest.
3. **Keep the irreducible seam explicit.** Use a relationship table for action, temporal, and episode membership rather than pretending that collection membership or source lineage answers the task-dependence question.
4. **Make the guarantee executable.** Generate a split receipt and reject protected-group crossings, unresolved relationships treated as independent, and silent loss of many-to-many membership.
5. **Choose the formal home after use.** Let the pilot reveal whether the stable semantics belong in an existing PDS construct, an LDD update, an OGC extension or encoding, or a linked Planetary Data Ecosystem artifact.

## Strongest counterposition

The strongest counterposition is that no new standard work is needed. SomBench and MCTED show that competent benchmark builders can define group-aware splits, publish assignments, and document their logic today. TrainingDML-AI already provides a broad, extensible information model.

That counterposition is partly correct. The proposed pilot earns its burden only if mission-linked relationship data materially reduce repeated reconstruction, contradictory grouping, or unauditable evaluation. If one task can be handled accurately by a small external manifest with no durable archive role, the correct outcome is to keep it external. If the grouping semantics cannot be reviewed or maintained, the pilot should narrow or stop.

## Claims this crosswalk does not support

- It does not establish that PDS, TrainingDML-AI, SomBench, MCTED, or Lunaris is defective.
- It does not establish observed leakage in an Artemis II model or benchmark.
- It does not establish that the proposed fields are globally novel.
- It does not establish OGC conformance, PDS compatibility, or a required standards change.
- It does not turn reconstructed Artemis action or episode keys into official mission identifiers.
- It does not prove that preserving declared groups establishes statistical independence, label validity, calibration, representativeness, or external generalization.

## Specialist decisions still required

1. Which Artemis II keys, if any, can be mission-authoritative?
2. Can current PDS classes or dictionaries carry the proposed relationships without semantic distortion?
3. Should an OGC-aligned task profile be encoded with TrainingDML-AI or only mapped conceptually during the pilot?
4. What canonicalization and versioning rules should govern the split receipt?
5. Which broader scene, operator, time, target, or event dependencies remain outside the proposed manifest?
